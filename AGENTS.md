# AGENTS.md

StagingStudio — AI-assisted home staging lookbook generator for Circle G Designs (single tenant, one firm). Next.js 16 App Router + TypeScript, Supabase (auth + Postgres + storage), Prisma, Vercel AI SDK (`ai` + `@ai-sdk/openai`, GPT-4o-mini copywriting), Alibaba Cloud DashScope (qwen-image-2.1-pro inpainting — issue #1240) and OpenAI GPT-Image (`gpt-image-2.6-flare` inpainting — issue #1506), Browserless.io (PDF export).

## Commands

```bash
cp .env.example .env.local   # required before dev; all keys listed under "Env vars"
ln -s .env.local .env        # required before Prisma CLI commands (see env-file note below)
npm install                  # package-lock.json is committed; postinstall runs `prisma generate`
npm run db:push              # run once before dev; schema-first workflow
npm run dev
npm run db:generate          # after editing prisma/schema.prisma (regenerates client)
npm run db:studio
npm run lint                 # oxlint . (#1276). 87+ built-in rules across nextjs/typescript/react/jsx-a11y/correctness; 50-100× faster than eslint, native TypeScript 7 support. Replaces the previous eslint 9 flat-config chain (eslint-config-next@16.3.8 + eslint-plugin-jsx-a11y@6.10.2 + eslint-plugin-react@7.37.5) which was blocked from ESLint 10 by the latter two plugins' `^9` peer caps.
npm run typecheck            # tsc --noEmit
npm test                     # vitest run (tests live in tests/)
npx vitest run tests/auth-redirect.test.ts   # single test file
npm run e2e                  # hermetic Playwright browser suite; needs Docker (see Testing)
npm run e2e:headed           # same Playwright suite in a visible browser (debugging specs)
npm run build
scripts/dev-tunnel.sh        # local PDF export only: public tunnel (cloudflared/ngrok) + rewrites NEXT_PUBLIC_APP_URL in .env.local; `reset` restores localhost. Restart `npm run dev` after either.
```

- No formatter config; CI exists (`.github/workflows/ci.yml`) but run lint, typecheck, and build (and `npm test` if you touched logic with tests) locally before finishing a change.
- Prisma uses `db push`, not migrations — there is no `prisma/migrations/` dir and no migration history to maintain.
- Prisma CLI (`db push`, `db studio`, `migrate`) loads env vars only from `.env` — it does NOT read Next.js's `.env.local`. Keep a `.env → .env.local` symlink (both names gitignored) so Prisma and Next.js share one source of truth; without it, `npx prisma db push` fails with `Environment variable not found: DATABASE_URL` even when `.env.local` is fully populated.
- **Node version: pinned to 24.x LTS (Krypton) — see `.nvmrc`.** The Dockerfile (`builder` and `runner` stages) and `.github/workflows/ci.yml` both use `node:24-slim` / `node-version: '24'`. Do not run `npm` on Node 22 or 26 without first updating all three (`.nvmrc`, `Dockerfile`, `ci.yml`) and `package.json#engines.node` together. Per the upstream release schedule (nodejs.org/en/about/previous-releases), v22 is still LTS but on its way to Maintenance; v24 is the current Active LTS; v26 is Current (not yet LTS). Production deploys use whichever Node the Dockerfile pins, NOT the host's installed Node.

## Shell environment (rtk)

- **The `rtk ` prefix on shell commands is injected, not typed.** A global opencode plugin (`~/.config/opencode/plugins/rtk.ts`) intercepts every bash command before execution and runs it through `rtk rewrite`, which rewrites recognized commands to run under the rtk token-saving proxy (binary at `~/.local/bin/rtk`). Seeing `rtk git status` echoed in tool output when you wrote `git status` is expected — don't "correct" the command, don't add or strip the prefix yourself, and never treat the plugin as a repo problem to fix (it's user-global config, not project code).
- **Rewrites can change shape, not just prepend.** Observed with this install: `npm run lint` → `rtk lint`, `cat f` → `rtk read f`, `npx vitest run tests/auth-redirect.test.ts` → `rtk vitest tests/auth-redirect.test.ts`, `npx prisma db push` → `rtk prisma db push`. Not everything is rewritten — `npm test` passes through raw. Rules live in rtk's internal registry; preview any rewrite with `rtk rewrite '<cmd>'`.
- **Output is filtered before you see it** (60–90% smaller): `git status`/`diff`/`log` compacted, test runners show failures only (passing tests collapse to a count), `ls` becomes a file-count tree, `grep`/`rg` group matches by file. Absence of output is not evidence of absence: a green `rtk npm run e2e` may show just `ok`, missing warnings ≠ no warnings, and Playwright failure tracebacks are trimmed (full artifacts land in `test-results/`). When compact output looks suspicious or you need exact raw output, prefix the command with `rtk proxy` (`rtk proxy npm run e2e`) or add rtk's `-v` flag.
- **rtk meta commands:** `rtk --version` (verify binary), `rtk rewrite '<cmd>'` (preview rewrite), `rtk gain` (savings stats), `rtk proxy <cmd>` (run unfiltered).

## Testing

- Two runners, deliberately split: vitest owns pure-logic unit tests (`tests/**/*.test.ts` — the `tests/` root **and** the `tests/lib/`, `tests/api/`, `tests/actions/` subdirectories; its config excludes `tests/e2e/**`), Playwright owns browser specs (`tests/e2e/specs/` — 24 `*.spec.ts` files on this checkout: `batch-staging`, `breadcrumb`, `edit-room-redesign-copypanel`, `edit-room-redesign-finetune-feather`, `edit-room-redesign-mask-paint`, `edit-room-redesign-run-button`, `edit-room-redesign-scope-switch`, `edit-room-redesign-version-strip`, `editor-layout`, `export-pdf`, `export-pdf-v1`, `export`, `inpaint-quota-ledger`, `inpaint-submit`, `lookbook-edit`, `lookbook-print-baseline`, `lucide-icons`, `mask-paint`, `preview`, `rehearsal`, `signoff`, `studio-workflow`, `upload`, `version-history`). Don't move specs between them.
- **Unit tests live in `tests/` *and* `tests/lib/` (plus `tests/api/` and `tests/actions/`) — never audit coverage with a flat `ls tests/*.test.ts`.** A flat `ls` sees only the 198 files in the `tests/` root and misses all 40 files in the subdirectories, 19 of them in `tests/lib/`. That miss produces phantom "untested module" findings for every module whose only pin lives in a subdirectory — 15 modules are pinned *only* from `tests/lib/` today (`ai-route-schemas`, `api-errors`, `api-logging`, `api-version`, `circuit-breaker`, `cors`, `env`, `error-tracking`, `events`, `logger`, `rate-limit`, `retry`, `sanitize-copy`, `setup-rate-limit`, `sliding-window-ratelimit`). Audit instead with `find tests -name '*.test.ts'` (238 `*.test.ts` files, plus 23 `*.test.tsx` component tests, on this checkout) and then grep each test's **import path** (`@/lib/<name>` or a relative `../src/lib/<name>`) to learn what it actually pins. Filename equality is a convention only, never an enforced invariant — a test may be named after the module, pinned from a different directory, or pinned under a completely different name.
- **The required checks are three separate jobs, not one combined check.** Since #1490 the single combined lint+typecheck+vitest job in `ci.yml` was split into three independent parallel jobs — one per command — whose job display names are **`Lint`**, **`Typecheck`** and **`Unit tests (vitest)`**. **Both `develop` and `main` require exactly those three display names** (and nothing else). In GitHub's branch-protection dropdown they appear under the `CI` workflow by those names; the old single combined display name was removed with the old job, so searching for it — or for the old job id — finds nothing. `E2E (Playwright)` is deliberately *not* required (it only runs on `push`; see below).
- `npm run e2e` is hermetic — no real credentials or paid services. Playwright global setup spins up a throwaway Dockerized Postgres (pushes schema, seeds fixed rows) plus a local mock Supabase (GoTrue auth + Storage) and a local mock Browserless, so the dummy API keys are never exercised. Runs against a production build, single worker for determinism. Requires Docker and `npx playwright install chromium`. Run it when touching upload/inpaint/export flows. Failure artifacts land in `test-results/` and `playwright-report/` (both gitignored). Do not gate the hermetic Browserless override on `NODE_ENV` instead of `E2E_HERMETIC`: the e2e suite runs a production build, so `NODE_ENV` is already `"production"` in the one run that needs the override. **CI runs this suite too**, as the `e2e` job in `ci.yml` — but scoped to `push` on `develop`/`main`, not `pull_request`. Push-only is a **cost / non-blockability trade, not a branch-protection fact**: feature branches do get PRs and `pull_request` runs (the `Lint`/`Typecheck`/`Unit tests (vitest)` jobs fire there), but the browser suite needs no secrets (everything is mocked) yet is not cheap — a production build plus 95 single-worker specs (95 `test()` cases across the 24 `*.spec.ts` files — `grep -hoE "test\(" tests/e2e/specs/*.spec.ts | wc -l`) — so one run per merge beats one run per PR push. Two consequences to remember: a red e2e run does **not** block the merge that caused it, and the job therefore cannot be a required check (a skipped job cannot be required). `main` gets its own run on release, so a release-merge regression surfaces in the same place the Production deploy does.
- **Two mocking strategies, and the difference matters (#1084).** Most specs mock a route at the *browser* layer with `page.route`, so the real handler never runs — fine for client-side behavior (toasts, optimistic UI), but it means auth, validation, quota, and upstream-error mapping go untested. `export-pdf.spec.ts` and `export-pdf-v1.spec.ts` deliberately do the opposite and run the *real* `/api/export-pdf` and `/api/v1/export-pdf` handlers, which need a different seam: the handler's outbound Browserless fetch happens in the Next.js **server** process, and `page.route` only intercepts browser-context traffic, so a `page.route` glob on `chrome.browserless.io` silently never fires (it once made the suite call the real paid API with a dummy key and assert against its 401). That handler's endpoint instead resolves through the hermetic-gated `E2E_BROWSERLESS_PDF_URL` override to `mock-browserless.ts`. **When a spec needs a route's server-side behavior, reach for an env-gated endpoint override, not `page.route`.** Note the two export routes disagree on upstream-error mapping: the unversioned one propagates the provider's status rather than normalizing (a 503 upstream surfaces as 503), while `/api/v1/export-pdf` flattens the same 503 to a 500 `invalid-request`. Both behaviors are pinned by their specs — check which route you're asserting against before assuming. A third lever, for the daily quotas those routes enforce: the counters are **rows in the suite's Postgres**, so a spec reaches a 429 by seeding one (see `withExportUsageAtLimit` in `tests/e2e/quota.ts`) rather than by setting `DAILY_EXPORT_LIMIT: "0"` in `nextEnv()` — that env is process-wide and would 429 every export spec in the run, including the success paths.
- **The mock Browserless's captured-request log is process-wide and shared for the whole suite run** (`mockBrowserlessRequests()`), and `playwright.config.ts` pins `workers: 1` so specs are sequential. A spec that needs its *own* provider calls must slice the log by a count delta taken before the request — never index from `0`, which picks up an earlier spec's calls. `export-pdf-v1.spec.ts` uses a local `freshBrowserlessRequests()` helper for this.

- The git remote is `anchapin/staging-studio` (not `stagingstudio/staging-studio`). Use `anchapin/staging-studio` for all `gh` CLI commands and GitHub API calls.

## Security advisories

- **`braces` CVE-2026-93687 / GHSA-vfj7-8cjw-p6xm (dev-only transitive) — tracked in #1220.** `npm audit` chains 9 high-severity reports through `braces` → `micromatch` → `fast-glob`, reached in this repo only via the `shadcn` CLI (build-time) and the historic `eslint-config-next`/`@next/eslint-plugin-next` dev lint chain (still in older lockfile entries). **No `src/`, `middleware.ts`, server-action, or API-route code imports any of them** (verified via `grep -rn "fast-glob\|micromatch\|braces" src/`). The upstream `braces` maintainer (`@jonschlinkert`) refuses to issue a fix and calls the CVE itself "complete nonsense" (`micromatch/braces#70`); the advisory lists "Patched versions: None". `npm audit fix --force` is not a viable resolution: it would downgrade `shadcn@4.21.4` → `1.0.0` (which lacks `tailwind.css`, breaking the `globals.css` `@import` of `shadcn/tailwind.css"` at runtime) **and** would unwind #1183's CRITICAL `next/og` RCE patch (`next: ^16.3.5 → ^16.3.8`) — the wrong trade. We instead apply `package.json#overrides.braces = "npm:@dieub/braces-depth-guard@3.0.3-pn.3"` (a depth-guarded backport maintained outside the upstream) so every consumer transparently uses the patched fork — `npm audit` reports 0 vulnerabilities. **Re-audit at each `npm install`** (`npm audit` should stay clean); if `@dieub/braces-depth-guard` is ever abandoned, fall back to either (a) accepting the advisory with a documented exception in a CI allow-list or (b) revisiting once `braces` releases a fix upstream. **Revisit trigger (any of):** `#1220`'s resolution criteria are met (patched `braces` ships, or one of the three transitive chains — `eslint-config-next`, `shadcn`/`@shadcn/registry`, `ts-morph` — swaps `fast-glob` for a `braces`-free globber, or `npm audit` reports fewer than 9 advisories with `npm ls braces` resolving to `>3.0.3`). Until then, **do not run `npm audit fix --force`**. Investigation handoffs: `.handoffs/2026-10-07-braces-cve-{dev-only,tracking-issue-and-dirty-tree,repair-complete}.md`.

## Routing & auth

- Real URLs: `/` (server-side auth redirector), `/login`, `/setup` (in `(auth)` group), `/signup` (top-level redirect stub → `/login`, where Magic Link creates accounts on first use; deliberately NOT in the `(auth)` group — added by #533 to fix #465, it only renders the root layout), `/dashboard`, `/settings`, `/projects`, `/projects/new`, `/projects/[id]` (in `(dashboard)` group) with five studio sub-pages: `/projects/[id]/setup` (project intake, first workflow-stepper step), `/projects/[id]/rooms` (per-room staging studio), `/projects/[id]/refine` (staged-result refinement, `?room=`-scoped), `/projects/[id]/lookbook` (interactive lookbook editor + ROI metrics), `/projects/[id]/report` (client-facing consultation report with comparison slider); `/preview/[id]` (in `(print)` group — standalone cookie-less print route that Browserless fetches for PDF export), `/auth/callback` (route handler, real segment).
- Route-group membership is not uniform: the `/dashboard` page sits OUTSIDE the `(dashboard)` group while `/projects/*` and `/settings` sit inside, and neither `/auth/callback` nor `/signup` is in `(auth)`. Don't "normalize" this without checking which layout wraps what.
- Auth protection lives in root `middleware.ts`, not in folder names, and the redirect rules are centralized in `src/lib/auth-redirect.ts` (`resolveAuthRedirect`, pinned by `tests/auth-redirect.test.ts`). It validates sessions with `supabase.auth.getUser()` (real JWT check, fails closed). Protected prefixes are `/dashboard`, `/projects`, and `/settings`; unauthenticated → `/login`, authenticated on `/login` → `/dashboard`. Guards use `startsWith` prefix matching (so `/projectsXYZ` counts as protected) — surprising but pinned by tests; don't "fix" it. `/setup` passes through in BOTH directions: middleware runs on the edge runtime and cannot consult Postgres, so the setup page self-guards server-side (`resolveSetupPageTarget`) — an authenticated user WITHOUT a Prisma `User` row must still reach setup instead of dead-ending. Any new protected route must be added to `resolveAuthRedirect` (and its test). Middleware does NOT guard `/api/*` — API routes and server actions enforce sessions and ownership themselves (via `src/lib/api-auth.ts`); every new mutation endpoint must do the same.
- Redirect targets differ and that's intended: `/` sends authed users to `/projects`; middleware and the auth callback send users to `/dashboard`. The auth callback fails SAFE: a Prisma lookup error still lands on `/dashboard`, where the dashboard layout bounces row-less users to `/setup`.
- Lookbook preview access is token-based, not session-based: `api/export-pdf` mints a 30-minute HMAC token (`lib/preview-token.ts`, `PREVIEW_TOKEN_TTL_SECONDS`, #1109) scoped to one projectId and appends it to the preview URL; the print page verifies it itself and 404s on invalid/expired/mismatched tokens. Sign/verify use Web Crypto (`crypto.subtle`), NOT `node:crypto` — required because middleware runs on the Edge runtime. Respect that constraint for any new crypto in middleware-path code.
- Middleware refreshes auth cookies on every matched request. Server Components can only read cookies — the try/catch-and-ignore around `cookieStore.set` (see `src/app/page.tsx`) is intentional, not a bug.

## Vercel CLI env commands (#1100)

The Vercel CLI's `env` subcommands look like a free source of truth for the keys above, and they are — but they are also a footgun. Read this before running any of them.

- **Never run bare `vercel env pull`.** With no path argument, the CLI writes to `.env.local` — which in this repo is the app's real env file AND the target of the `.env → .env.local` symlink the Prisma CLI depends on. The command will silently overwrite your entire local environment and break the symlink in one shot. (#1100 lost 4 credentials this way.) **Always pass an explicit path**: `vercel env pull .env.vercel-backup` (or any other filename that isn't `.env.local` / `.env`). `vercel env pull .env.local` itself is the same footgun — the override must be a different file.
- **Vercel is not a backup. Secrets are unrecoverable.** Only variables of Vercel `Config` type are returned by `env pull`. Secrets (the `Sensitive` / encrypted type) are not, and there is no CLI or dashboard path to retrieve a secret value once it has been set — only to rotate it. That means any key that you stored as a Secret (including, historically, `BROWSERLESS_API_KEY` and `OPENAI_API_KEY` before they were migrated to `Config` for this very reason) must live somewhere durable outside Vercel, or it is one project reset away from gone. `DATABASE_URL` and the API keys above all need an off-Vercel source of truth.
- **`vercel env ls`'s `created` column is not a sync signal.** That timestamp is set when the variable was first created and is not bumped when the value is rotated in place via `vercel env add`. A matching `created` on local and remote is not evidence that the two are in sync; it only means both rows were created at the same moment. Diff values, not timestamps.
- **Strip surrounding quotes from any pulled `DATABASE_URL` before Prisma will accept it.** Vercel stores the Postgres URL with double quotes around it, and `env pull` writes them through verbatim. Prisma's CLI reads the raw value from `.env` and the surrounding `"` makes the connection string unparseable, so `npx prisma db push` then fails with a connection error that does not point at the quoting. After pulling, grep for `^DATABASE_URL=` and remove the wrapping quotes by hand (or pipe through a one-liner) before running any Prisma command.
- **Re-check `.gitignore` after any Vercel CLI command.** `vercel env pull` will write a new path into `.gitignore` for you, and the ordering constraint on `!.env.example` (which has to come AFTER the broad `.env*` rules to keep the template tracked) is easy to break silently if the CLI appends above it. After every `env pull` / `env add`, `git diff .gitignore` and confirm `!.env.example` is still in the ignore-negation block — if not, `git checkout HEAD -- .gitignore` and re-add the pull path manually below the negation.

## Toolchain quirks

- Tailwind v4 runs CSS-first (`@import "tailwindcss"` in `globals.css`) but still loads the legacy JS config via `@config "../../tailwind.config.ts"`; PostCSS uses `@tailwindcss/postcss`. Don't reintroduce v3 `@tailwind` directives.
- `next.config.ts` allowlists remote images only for `*.supabase.co` and `*.fal.ai` — a new image host must be added to `images.remotePatterns` or `next/image` throws. Note: the inpaint surface (Alibaba DashScope) generates images on DashScope's OSS and uploads to Supabase Storage within the 24h URL validity window, so the browser never requests DashScope URLs directly — no allowlist change needed for the migration.
- shadcn style is `base-nova`; add components via the CLI (`npx shadcn@latest add …`) so `components.json` aliases stay in sync.
- **Next.js rewrites `tsconfig.json` on every build/dev** (root cause #193): Next 16.3.5's `getDesiredCompilerOptions()` requires `jsx: "react-jsx"`, so `next build`/`next dev` unconditionally flips the committed `"jsx": "preserve"` → `"react-jsx"` (and manages the `.next/dev/types` include) — no opt-out; the `extends` escape hatch disables Next's tsconfig setup entirely (rejected). The committed tsconfig is authoritative: expect this dirty state after every build/dev and NEVER commit the flip — `git checkout HEAD -- tsconfig.json` before committing. Use the **HEAD form**: bare `git checkout -- <file>` restores the working tree from the *index*, so a flip that is already **staged** is restored straight back and the guard stays blocked with no visible progress. Guard: `scripts/enable-hooks.sh`, wired as the `prepare` lifecycle script, sets `git config core.hooksPath .githooks` on `npm install` — so a fresh clone is protected without a manual step (#1095). That activates the committed pre-commit hook `.githooks/pre-commit`, which `exec`s `scripts/check-tsconfig-flip.sh` to fail the commit when the only tsconfig diff is this flip (#219). Run it by hand (`bash scripts/enable-hooks.sh`) if you need to re-check. It is deliberately inert-safe: it exits 0 when there is no `.git` (Docker `npm ci`, published tarballs), never clobbers a `core.hooksPath` you set deliberately, and warns when the hook is not executable. Both files are committed `100755` — that mode is load-bearing, since git silently skips a non-executable hook. If you ever see `hint: ... hook was ignored because it's not set as executable`, the guard is inert and you are back to reverting the flip by hand.

## Domain model

`prisma/schema.prisma`: `User` (firm branding, editable page templates, `darkMode` preference) → `Project` (one staging job: address, client, target buyer, `stagingAesthetic`, `stagingPackage`, project-wide `stagingDirectives`, `buyerDemographics` JSON, ROI trio `roiSalesPricePremium`/`roiTransactionVelocity`/`roiInvestmentTier`, and client sign-off — `clientSignature` PNG data URL, `clientSignatureStatus` `"Pending" | "Signed"`, `clientSignatureTimestamp` set when signed; lifecycle Pending → Signed with timestamp, persisted via `/api/sign-project`, already-signed projects refused) → `Room` (two before/after image variants, selected variant index, AI outputs: raw directives, observed challenge, recommendation, buyer psychology, checklist JSON) → `InpaintRequest` (Alibaba Cloud DashScope queue request mapped to a room + variant slot; status and durable result URL; cascade-deleted with its room). Room-scoped satellites also cascade with their room: `InpaintVersion` (per-variant-slot version history — result URL, thumbnail, seed, prompt directives — that version restore/compare reads) and `SelectionLog` (durable per-instance concept toggle telemetry for the training-corpus export). Project-scoped satellites cascade with their project: `MaterialSwatch` (finish/palette rows shared across a project's rooms) and `ProcurementItem` (furniture procurement table rows with needed/ordered/received status). `VisionLabel` stands alone — a GPT-4o-mini label cache unique on `imageUrlHash + concept + instanceIndex` with score, no owner relation, so it survives deletes. Deletes cascade down the chain from `User`.

## Releasing to Production

- **`main` is the Production branch**; `develop` is where work lands. Vercel's git integration deploys `main` to Production. PR preview deploys are turned off, and the old `.github/workflows/preview.yml` CLI deploy path was deleted — it had never run successfully (see #1096). The repo has **two** workflows: `ci.yml` (the `CI` workflow — lint, typecheck, unit tests, the browser suite, the Docker image build and the release guard) and `add-to-project.yml`, which adds newly opened or reopened issues to the project board and no-ops with a notice when the `ADD_TO_PROJECT_PAT` secret is missing.
- **Nothing in the normal flow forces a commit that reaches `main` to also reach `develop`.** A hotfix merged straight to `main` therefore leaves `develop` self-consistent but **stale**: its code and its tests agree with each other, and both disagree with what actually ships. Nothing is *lost* by the merge (main's commits survive it), but the stale expectations surface only as **test failures at release-merge time**, when newer code is measured against older assertions. This is not hypothetical: before the #1097 release, `main` carried four hotfixes (`#1043`, `#1044`, `#1045`, `#1018`) that `develop` had never seen, and `#1018`'s response-header rename surfaced three failing e2e tests on the merged tree.
- **Guard:** `npm run release:check` (= `scripts/check-develop-catchup.sh [BASE] [HEAD]`, defaulting to `origin/main` vs `origin/develop`). It exits non-zero when `BASE` holds non-merge commits `HEAD` lacks, printing them plus the fix. It also runs in CI as the **`release-guard` job, scoped to `if: github.base_ref == 'main'`**, so it fires only on release PRs and costs ordinary PRs nothing. That job checks out with `fetch-depth: 0`, because the ancestor test needs real history rather than a shallow clone.
- **Merge commits are deliberately excluded** from the comparison. Every develop→main release makes `main` gain a merge commit `develop` can never contain, so counting merge commits would fail the guard immediately after every successful release. Hotfixes land as ordinary commits, which is exactly what must be caught.
- **Procedure:** back-merge `main` into `develop` so `develop` absorbs any hotfixes → open a `develop`→`main` PR → CI runs the three required jobs (`Lint`, `Typecheck`, `Unit tests (vitest)`) plus the `Release guard (develop caught up with main)` job → merge → Vercel deploys `main` to Production. The merge then triggers the `push`-scoped `E2E (Playwright)` job on `main` (see Testing), so a release-only browser regression shows up *after* the deploy rather than before it — check that run before the demo. Resolve merge conflicts *on a release branch* (branch from `main`, merge `develop` in, push, PR that branch) rather than asking GitHub to auto-merge a diverged pair.
- **`develop` and `main` are both protected with 0 required approving reviews, and both require the three `CI` checks `Lint`, `Typecheck` and `Unit tests (vitest)`.** Zero reviews because this is a solo-maintainer repo, so a 1-review rule is an unmeetable deadlock, and with `enforce_admins` on it was a permanent one; force-pushes and deletions stay blocked and `enforce_admins` stays on, so a stray direct push is still stopped while a self-merge is permitted. The required checks are the **jobs' `name:`** fields, not their ids — since #1490 the former single combined job was split into three parallel jobs in `ci.yml`, and in GitHub's branch-protection dropdown the `CI` workflow's three jobs appear as `Lint`, `Typecheck` and `Unit tests (vitest)`; searching for the old combined display name or for the removed job id finds nothing. Do **not** also require `Vercel Preview Comments`: with preview deploys off it may stop reporting, and a required check that stops reporting blocks every future PR. Note these three checks cover lint + typecheck + vitest but **not** the e2e suite, so required checks are not the same as a fully verified release. The `e2e` job does run in the same workflow, but on `push` only (see Testing), which puts browser coverage one step *after* the merge rather than before it — and a job that skips on a PR can't be required anyway. Only add `E2E (Playwright)` to protection if its `if` is widened to cover `pull_request` too.
- **Branch protection also has "require branches to be up to date" enabled** (`strict`). For a `develop`→`main` release PR that means the head must already contain `main`'s tip, so the back-merge in the procedure above is enforced by GitHub rather than merely recommended. It complements `release-guard` rather than duplicating it: CI fails with a readable commit list at PR time, GitHub blocks with a generic "branch is not up to date".
